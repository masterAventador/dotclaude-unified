# 验证事故与检查方法（按需查阅）

本文件解释历史事故与排查方法；执行要求以 `../CLAUDE.md` 为准。

## 区分“没有”和“没查”

曾多次将“零结果”和“检查根本没执行”混为一谈。关键问题是：目标确实存在或命令失败时，检查能否给出不同结果？

| 情形 | 容易遗漏的事实 | 检查方法 |
|---|---|---|
| zsh 的 `ls a* b*` | 默认无匹配报错时，一个 glob 无匹配可能阻止整条命令执行 | 分开检查或使用明确处理无匹配的查找方式 |
| `cd X && cmd1` 后另起一行执行 `cmd2` | `cd` 失败不阻止独立的 `cmd2` | 明确工作目录，让依赖步骤遇错即停 |
| 等待循环里 `pgrep -f "任务名"` | 可能匹配包含该字符串的循环自身 | 使用记录的 PID 或专用标识，并排除查询自身 |
| `cmd` 输出经 `tail` 截取 | 关键结果可能在被截掉的部分，管道退出码也可能来自末端 | 保留完整日志，定向读取关键标记并检查被测命令状态 |
| 带过滤器运行测试 | 零个匹配测试也可能退出 0 | 确认目标测试名称与实际执行数量 |
| `cmd > log 2>&1; echo "exit=$?"` | 打印内容是 `cmd` 的退出码，但整段 shell 最终状态通常来自 `echo` | 及时保存退出码，打印后按原退出码退出 |

退出码示例：`false; echo "exit=$?"` 打印 `exit=1`，不能误写为“打印值永远为 0”。
如果需要把失败传递给调用方，可保存状态后再退出：

```sh
cmd > log 2>&1
result_code=$?
printf 'exit=%s\n' "$result_code"
exit "$result_code"
```

这些例子不意味着禁止批量或并行检查；独立检查逐项收集结果，有依赖的步骤顺序执行即可。

## 测试构建掩盖缺失的生产依赖

曾有桌面产品在测试构建中通过环境变量读取验收脚本临时构建的运行时依赖，而正式构建从安装包资源目录读取。
功能测试长期通过，正式包却没有装配该依赖，也没有出包门禁拒绝缺失资源，导致用户无法使用。

因此必须验证实际交付包与运行时依赖装配，不允许测试专用捷径掩盖生产缺陷。
问题不在于环境变量、平台适配或所有构建差异本身；应检查实际配置解析路径、依赖是否随包交付，以及用户拿到的包能否走通核心链路。
